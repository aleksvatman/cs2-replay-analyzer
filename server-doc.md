# Сервер на Axum: спецификация

Сервер принимает файл `.dem`, разбирает его библиотекой `parser-core` и отдаёт приложению готовый компактный JSON. Это тонкая обёртка: вся логика разбора живёт в `parser-core`. Общий план проекта: `plan.md`, формат JSON: `docs/format.md`, спецификация парсера: `parser-doc.md`.

## 1. Цель и границы первой версии

Сервер нужен, чтобы iPad не разбирал демки сам: приложение загружает файл, ждёт окончания разбора и скачивает JSON. Тот же JSON приложение сможет получить локально через `ios-bridge`, поэтому формат на сервере и на устройстве одинаковый.

Входит в первую версию: загрузка демки, очередь разбора с прогрессом, хранение результатов на диске, выдача списка матчей, статуса и JSON, удаление матча, авторизация простым токеном, Docker и деплой на VPS.

Не входит: учётные записи и разделение данных между пользователями (один токен на всё), база данных, веб-интерфейс, потоковая выдача по частям, кластер из нескольких серверов.

## 2. Правило: парсер не меняем

Работа над сервером не должна менять `parser-core/` (код, тесты, `Cargo.toml` крейта), эталоны в `samples/`, `docs/format.md` и `docs/measurements.md`. Сервер использует только публичный API `parser-core`: `parse_file`, `parse_bytes`, `to_json`, `write_json`, `parse_file_to_json`, `Progress`, `Stage`, `ParseError`.

Если изменение парсера всё же понадобится (например, отмена разбора или хук прогресса внутри прохода), его не делают самостоятельно: сначала описывают владельцу, что и зачем менять, и ждут подтверждения. Каждый этап сервера перед коммитом проверяет, что `git diff --stat main -- parser-core samples docs/format.md docs/measurements.md` пуст.

## 3. Стек

Rust (stable), единый Cargo workspace с `parser-core`. Зависимости сервера: `axum`, `tokio`, `tower-http` (лимиты, сжатие, трассировка), `uuid`, `serde`, `serde_json`, `tracing` и `tracing-subscriber`, `sha2`, `flate2`, `parser-core`. Для тестов: `tower`, `http-body-util`, `tempfile`.

## 4. Структура крейта `server/`

- `Cargo.toml` зависимости выше; workspace-корень объединяет `parser-core`, `server`, позже `ios-bridge`.
- `src/main.rs` запуск, сборка маршрутов, общее состояние, остановка.
- `src/config.rs` конфигурация из переменных окружения.
- `src/state.rs` общее состояние: хранилище, очередь, конфиг.
- `src/error.rs` тип ошибки и единый формат ответа.
- `src/api/upload.rs` приём файла, создание задачи, возврат id.
- `src/api/matches.rs` список, статус, выдача JSON, удаление.
- `src/api/health.rs` проверка живости.
- `src/jobs.rs` очередь разбора, семафор, запуск `parse` в `spawn_blocking`, статусы и прогресс.
- `src/storage.rs` файлы на диске, атомарная запись, восстановление при запуске, очистка.
- `tests/` интеграционные тесты.
- `Dockerfile`, `.dockerignore`.

## 5. API первой версии

| Метод и путь | Назначение |
|---|---|
| `POST /matches` | загрузить демку (тело запроса: байты файла), ответ `202` с `id` и статусом |
| `GET /matches` | список матчей: id, статус, карта, дата загрузки, размер |
| `GET /matches/{id}` | статус, стадия и процент разбора, ошибка, краткая сводка (карта, счёт, число раундов, `schemaVersion`) |
| `GET /matches/{id}/data` | полный JSON (только для статуса `done`, иначе `409`) |
| `DELETE /matches/{id}` | удалить матч и его файлы |
| `GET /health` | `200 ok`, без авторизации |

Ошибки всегда JSON вида `{"error": {"code": "…", "message": "…"}}`. Коды: `400` плохой запрос (в том числе оборванная загрузка), `401` нет или неверный токен, `404` нет матча, `408` клиент перестал присылать данные, `409` данные ещё не готовы, `413` файл больше лимита, `429` слишком много запросов или одновременных загрузок (с `Retry-After`), `507` на сервере уже `MAX_MATCHES` матчей, `415` неверный тип содержимого, `422` не демка CS2 или разбор не удался, `503` очередь переполнена.

Загрузка принимает «сырое» тело: заголовок `Content-Type` либо `application/octet-stream`, либо `application/x-www-form-urlencoded` (его по умолчанию ставит `curl --data-binary`), либо отсутствует; `multipart`, JSON и текст получают `415` с подсказкой отправлять файл сырым телом. Тип не определяет безопасность: тело не разбирается, проверяются сигнатура и размер, а защита от чужих запросов это токен (этап 6). Пример: `curl -H "Content-Type: application/octet-stream" -H "X-File-Name: match.dem" --data-binary @match.dem localhost:8080/matches` . Необязательный заголовок `X-File-Name` сохраняется в `meta.json` как справочная информация. Новый матч: `202`; если такая демка уже есть (по SHA-256, кроме матчей в `failed`), `200` с id существующего матча. Сжатые демки (gzip) в первой версии не принимаются: лишний распаковщик не нужен.

## 6. Задачи и статусы

Статусы: `queued` → `parsing` → `done` или `failed`. В `parsing` у матча есть `stage` (из `Stage` парсера: Events, Players, Grenades, Assemble, Done) и `percent` (0-100, монотонный).

Разбор тяжёлый по процессору, поэтому запускается через `tokio::task::spawn_blocking`; колбэк `Progress` обновляет состояние задачи в общем состоянии. Приложение узнаёт о ходе разбора опросом `GET /matches/{id}` (polling раз в 1-2 с). SSE и WebSocket в первой версии не нужны.

Ошибка `ParseError` или паника (парсер ловит её сам через `catch_unwind`) переводит задачу в `failed` с текстом причины; сервер при этом не падает. Сервер не собирается с `panic = "abort"`.

## 7. Ограничение нагрузки

По `docs/measurements.md` один разбор полного матча занимает около 9 с на M1 Pro и около 0,9 ГБ RSS (footprint 350-370 МБ). Поэтому число одновременных разборов ограничено семафором (`MAX_PARALLEL_PARSES`, по умолчанию 1 или 2). Остальные задачи ждут в очереди со статусом `queued`. Если очередь длиннее лимита (`MAX_QUEUE`), новая загрузка получает `503` с заголовком `Retry-After`. На VPS нужно закладывать память не меньше 2 ГБ на один параллельный разбор с запасом.

## 8. Загрузка больших файлов

Демки весят сотни мегабайт (полный матч 410 МБ), поэтому:

- тело запроса стримится на диск порциями, в памяти файл целиком не держится;
- размер ограничен (`MAX_UPLOAD_BYTES`, по умолчанию 1 ГиБ); `Content-Length` проверяется сразу, фактический размер контролируется при чтении;
- до постановки в очередь проверяется сигнатура `PBDEMS2\0` в первых байтах, не демка отклоняется с `422`;
- при обрыве соединения и любой ошибке частично записанный файл удаляется;
- запись идёт во временный файл и атомарно переименовывается, чтобы не оставить полузаписанную демку;
- таймаут на неактивное соединение, чтобы медленный клиент не держал дескрипторы бесконечно;
- имя файла от клиента не используется для пути (защита от `../`); имя хранится только как метаданные.

## 9. Хранилище

Каталог `DATA_DIR`, внутри `<id>/`:

- `match.dem` исходная демка (по настройке удаляется после успешного разбора);
- `match.json.gz` результат разбора, сжатый;
- `meta.json` статус, ошибка, время загрузки и разбора, размер, SHA-256 демки, карта, `schemaVersion`, краткая сводка.

Записи атомарные (временный файл и `rename`). При запуске сервер сканирует `DATA_DIR`, восстанавливает список матчей; задачи, оставшиеся в `queued` или `parsing` после перезапуска, ставятся в очередь заново, если `.dem` сохранён, иначе помечаются `failed`.

Дедупликация: по SHA-256 демки. Повторная загрузка той же демки возвращает существующий матч (`200` с тем же `id`), а не создаёт копию. Политика хранения: `RETENTION_DAYS` удаляет старые матчи фоновой задачей; отдельно можно оставлять только JSON, удалив `.dem`, чтобы экономить диск.

## 10. Выдача JSON

JSON уже лежит сжатым (`match.json.gz`, полный матч 19,2 МБ распакованный и 3,3 МБ сжатый). Клиенту с `Accept-Encoding: gzip` отдаётся файл как есть с `Content-Encoding: gzip`, остальным распаковывается на лету. Заголовки `ETag` (SHA-256 результата) и `Cache-Control` позволяют приложению не качать повторно. Размер ответа значительный, поэтому ответ не собирается в памяти целиком, а отдаётся потоком из файла.

`schemaVersion` попадает в сводку. Когда парсер обновляется и версия схемы меняется, старые результаты остаются валидными для старых клиентов, а новый разбор запускается командой `POST /matches/{id}/reparse` (если `.dem` ещё сохранён).

## 11. Безопасность

- Токен в заголовке `Authorization: Bearer …`, значение из `API_TOKEN`; без него на публичном адресе сервер не запускается (с явным флагом можно запустить без токена только на localhost для разработки). Сравнение токена в постоянное время.
- `GET /health` без авторизации.
- Лимиты: размер загрузки, число одновременных загрузок, число матчей на диске (`MAX_MATCHES`), частота запросов (rate limit на IP, по возможности).
- Только HTTPS снаружи (терминируется reverse proxy, см. деплой).
- Пользовательские данные в логи не пишутся: только id матча, размеры, стадии, время.

## 12. Конфигурация

Переменные окружения, у всех безопасные значения по умолчанию:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `BIND_ADDR` | адрес и порт | `127.0.0.1:8080` |
| `DATA_DIR` | каталог данных | `./data` |
| `API_TOKEN` | токен авторизации, не короче 16 символов (`openssl rand -hex 32`) | обязателен не на localhost |
| `MAX_UPLOAD_BYTES` | лимит загрузки | 1 ГиБ |
| `MAX_PARALLEL_PARSES` | параллельных разборов | 1 |
| `MAX_QUEUE` | длина очереди | 8 |
| `MAX_MATCHES` | матчей на диске (при заполнении загрузка получает `507`, даже повтор известной демки: проверка идёт до чтения тела) | 200 |
| `MAX_UPLOADS` | загрузок, принимаемых одновременно | 4 |
| `RATE_LIMIT_PER_MINUTE` | запросов в минуту с токеном, всего (0 = без лимита) | 600 |
| `RETENTION_DAYS` | срок хранения (0 = бессрочно) | 0 |
| `KEEP_DEM` | оставлять `.dem` после разбора | `false` |
| `RUST_LOG` | уровень логов | `info` |

## 13. Наблюдаемость и остановка

- Логи через `tracing`: id матча, стадия, длительность каждой стадии, размер результата, ошибки.
- Graceful shutdown по SIGTERM: перестать принимать новые загрузки, дать идущему разбору завершиться в пределах таймаута, остальное при следующем запуске восстановится из `DATA_DIR`.
- Метрики (число матчей, очередь, время разбора) пока только в логах.

## 14. Тестирование

Интеграционные тесты через `tower::ServiceExt` без реальной сети, на временном `DATA_DIR`; тесты на демках пропускаются, если нет `samples/test_demo.dem` (как в `parser-core`):

- загрузка короткой демки, опрос статуса до `done`, `GET /data` совпадает с эталоном `samples/test_demo.expected.json.gz` после распаковки;
- мусорный файл и пустое тело дают `422` и не оставляют файлов;
- превышение лимита даёт `413`, частичный файл удалён;
- без токена `401`, с неверным `401`;
- `GET /data` до готовности `409`; неизвестный id `404`;
- повторная загрузка той же демки возвращает тот же `id`;
- перезапуск (новое состояние на том же `DATA_DIR`) восстанавливает список и готовые матчи;
- переполненная очередь даёт `503`;
- `DELETE` убирает файлы.

Ручные проверки: полный матч 410 МБ через `curl`, память сервера под 2-3 параллельными загрузками.

## 15. Деплой

- Многоступенчатый `Dockerfile`: сборка release в образе Rust, запуск в минимальном образе; бинарник не root; том для `DATA_DIR`.
- VPS с памятью не меньше 2 ГБ (лучше 4), диск с запасом под демки (сотни МБ на матч, если `.dem` хранится).
- HTTPS через reverse proxy (Caddy или nginx), лимит тела запроса на прокси согласован с `MAX_UPLOAD_BYTES`, таймауты достаточны для медленной загрузки.
- Проверка живости: `GET /health`; перезапуск контейнера при падении.
- Резервные копии не нужны: данные восстановимы из демок; важен только `API_TOKEN` в окружении.

## 16. Риски

- Память: параллельные разборы складываются; держать семафор и лимит контейнера.
- Диск: демки большие; нужны `KEEP_DEM=false`, срок хранения и лимит `MAX_MATCHES`.
- Формат демок меняется после обновлений игры: при обновлении `demoparser2` возможен новый формат событий (как со строками в `round_end`); нужен повторный разбор старых матчей, поэтому `.dem` стоит хранить, пока не нужно место.
- Овертайм и паузы парсером не проверены (см. `summary.md`): сервер должен отдавать такие матчи как есть и не падать при ошибке парсера.
- Медленная загрузка по мобильной сети: нужны возобновление или повтор на стороне приложения; возобновляемая загрузка (по частям) в первую версию не входит.
- Нет CI с демкой: интеграционные тесты сервера на демке гоняются локально.

## 17. Этапы разработки сервера

Каждый этап: отдельная ветка от свежего `main`, PR после подтверждения, перед `push` обновлён `summary.md`, `parser-core` не изменён (правило из раздела 2).

1. **Каркас** (сделано). Крейт `server` в workspace, конфигурация из окружения, `GET /health`, тип ошибки с единым форматом, логирование, graceful shutdown. Зависимость от `parser-core` добавляется на этапе 4, когда появится разбор. Запуск: `cargo run -p server`, тесты: `cargo test -p server`.
2. **Хранилище** (сделано). `storage.rs`: каталог матча, `meta.json`, атомарная запись (временный файл, `fsync`, `rename`), id как UUID v4 (любая другая строка отвергается до построения пути), сканирование при запуске (`recover`: лишние `.tmp` удаляются, `queued`/`parsing` с сохранённой демкой возвращаются в `queued`, без демки становятся `failed`). Методы синхронные; вызывать из обработчиков внутри `spawn_blocking`, когда трогаются большие файлы. Прогресс разбора в `meta.json` не пишется.
3. **Загрузка** (сделано). `POST /matches`: стриминг на диск, лимит размера (по `Content-Length` и при чтении), проверка сигнатуры в первых 8 байтах, таймаут простоя 30 с, дедупликация по SHA-256 под общей блокировкой, очистка каталога при любой ошибке и при обрыве соединения. Матч создаётся в статусе `queued`; в очередь разбора его ставит этап 4. Незаконченные загрузки (каталог без `meta.json`) удаляет `recover` при запуске. Замер: демка 410 МБ принята за 1,6 с, память процесса сервера не выше 9 МБ.
4. **Очередь разбора** (сделано). `jobs.rs`: семафор на `MAX_PARALLEL_PARSES`, лимит «идущие + ожидающие» = `MAX_PARALLEL_PARSES + MAX_QUEUE` (сверх него `503` с `Retry-After`, проверка до чтения тела и ещё раз при постановке), разбор в `spawn_blocking` (паника или ошибка переводят матч в `failed`, сервер живёт), стадия и процент из колбэка `parser-core` хранятся в памяти (`Jobs::live`), результат пишется в `match.json.gz` потоком через gzip (временный файл и `rename`), `.dem` после разбора удаляется, если не задан `KEEP_DEM`. При запуске матчи, прерванные перезапуском, возвращаются в очередь (`resume`, лимит очереди к ним не применяется). Функция разбора подменяема (`Runner`), поэтому очередь тестируется без тяжёлого парсера. Замер (release, M1 Pro): полный матч 410 МБ разобран за 11,8 с, из них около 9 с сам парсер, остальное сжатие; пик памяти процесса сервера около 870 МБ; вторая демка ждала в очереди и разобралась после первой.
5. **Выдача** (сделано). `GET /matches` (массив строк, новые первыми: id, статус, карта, время загрузки, размер, имя, число раундов, счёт), `GET /matches/{id}` (то же плюс `stage`, `percent`, `parsedAt`, `schemaVersion`, `error`; стадия и процент идущего разбора берутся из `Jobs::live`), `GET /matches/{id}/data` (до готовности и для `failed` `409 not_ready`), `DELETE /matches/{id}` (`204`; пока матч в статусе `parsing`, `409 conflict`; ожидающий в очереди удалить можно, задача его пропустит). Счёт `[a, b]`: `a` команда, начавшая за T; считается при разборе по игрокам первого раунда (стороны меняются на полувремени) и хранится в `meta.json` (`rounds`, `score`). Данные: клиенту с `Accept-Encoding: gzip` (с учётом `q=0` и `*`) файл `match.json.gz` отдаётся как есть с `Content-Encoding: gzip` и `Content-Length`; остальным распаковывается на лету (поток из блокирующей задачи по каналу, файл целиком в памяти не держится). `ETag` = префикс SHA-256 демки, время разбора, размер файла и суффикс `-gzip` для сжатого варианта; `If-None-Match` даёт `304`; `Cache-Control: private, no-cache`, `Vary: Accept-Encoding`. Замер (release): полный матч, 19,7 МБ JSON отдан за 0,04 с, gzip и распакованный варианты совпадают, счёт 11:13 совпал с проверкой парсера.
6. **Безопасность** (сделано). Токен: с `API_TOKEN` все маршруты, кроме `GET /health`, требуют `Authorization: Bearer …` (схема без учёта регистра), проверка идёт до чтения тела загрузки (`401` с `WWW-Authenticate`); токены сравниваются в постоянное время (через SHA-256 обоих значений, поэтому длина настоящего токена не утекает); токен короче 16 символов сервер не принимает, без токена не запускается на не-loopback адресе; значение токена не попадает ни в логи (проверено при `RUST_LOG=debug`), ни в сообщения об ошибках конфигурации. Лимиты: `MAX_UPLOADS` одновременных загрузок (`429`), `MAX_MATCHES` матчей (`507`), общий rate limit по токену (ведро: всплеск на 10 с, то есть `RATE_LIMIT_PER_MINUTE / 6`, не меньше 5; `429` с `Retry-After`). Запросы без верного токена в rate limit не попадают, поэтому посторонние не могут исчерпать лимит владельца. Лимит один на всех, потому что токен один; за reverse proxy все запросы приходят с одного адреса, поэтому по IP лимит не делался. Остаётся на этап деплоя: HTTPS и лимит тела на прокси.
7. **Тесты и замеры.** Интеграционные тесты из раздела 14, нагрузка 2-3 параллельных загрузок, замер памяти, запись в `docs/measurements.md` (только по согласованию, раздел 2).

9. **Деплой.** `Dockerfile`, VPS, HTTPS, проверка живости, лимит тела на прокси, инструкция запуска.
