# Замеры parser-core

Снято на Apple M1 Pro, 16 ГБ, macOS, `cargo build --release`, rustc 1.89. Две демки: короткая `samples/test_demo.dem` (de_mirage, 58 МБ, 56 705 тиков, 10 раундов) и полный официальный матч `samples/natus-vincere-vs-falcons-m1-ancient.dem` (de_ancient, NAVI против Falcons, 410 МБ, около 207 тыс. тиков, 24 раунда, счёт 11:13 по результатам парсера). Обе в git не лежат. Команда: `/usr/bin/time -l cargo run --release -p parser-core --example parse -- samples/test_demo.dem out.json`.

## Полный матч (410 МБ, 24 раунда)

| Показатель | Значение |
|---|---|
| Время | 9,0 с (два запуска: 9,02 и 9,03) |
| Пиковый footprint | 350-370 МБ |
| Максимальный RSS | около 900 МБ (включает отображённый файл 410 МБ, вытесняемый системой) |
| JSON компактный | 19,2 МБ |
| JSON gzip | 3,3 МБ |
| Снимков игроков | 50 071 (по 10 игроков) |
| Точек траекторий гранат | 87 676 (561 граната) |

Время по шагам (с): события 2,7; снимки игроков 3,8; снаряды 2,5; сборка 0,3.

Разбивка JSON: `tracks` 83%, `grenades` 10%, `bomb` 4%, `ticks` 1%, остальное (события, сводки, статистика) меньше 1%.

Что показал полный матч:

- Время на тик выше, чем на короткой демке (23 тыс. тиков/с против 44 тыс.): в Ancient больше сущностей и игроков в движении. Предыдущая оценка 4 с для 170 тыс. тиков была слишком оптимистичной, реально 9 с.
- Footprint 350 МБ вместо оценки 250-300 МБ. Основная часть это колонки тикового прохода и записи снарядов.
- Размер JSON 19,2 МБ против оценки 15-16 МБ: раунды были длиннее среднего (много раундов 40-50 с).
- Оценка для iPad 7 (не измерена): в 4-6 раз медленнее Mac, то есть порядка 40-55 с, при footprint 350 МБ. Это нужно проверить на устройстве.

## Короткая демка (58 МБ, 10 раундов)

### Время

| Шаг | Время |
|---|---|
| Проход 1: события, ростер, раунды | 0,3 с |
| Проход 2: снимки игроков | 0,5 с |
| Проход 3: снаряды | 0,4 с |
| Сборка и статистика | 0,1 с |
| **Всего** | **1,3 с** (стабильно по трём запускам) |

Около 44 тыс. тиков в секунду. Время растёт линейно с длиной демки: поиск тиков в списке `wanted_ticks` проверен отдельно (список в 20 раз длиннее не изменил время), квадратичного роста нет.

Оценка по этой демке для полного матча (4 с) оказалась заниженной, см. выше.

### Память

| Показатель | Значение |
|---|---|
| Пиковый footprint (физическая память процесса) | около 100 МБ |
| Максимальный RSS | около 185 МБ |

Разница это страницы отображённого файла демки (58 МБ), которые система вытесняет при нехватке памяти. Три прохода идут по одному отображению файла. Память пропорциональна числу снимков и записей снарядов, а не размеру файла. Лимит приложения на iPad с 3 ГБ порядка 1,4-2 ГБ (оценка, не проверено), запас по footprint есть, но это нужно подтвердить на устройстве.

### Размер JSON

| Вариант | Размер |
|---|---|
| Компактный JSON | 5,3 МБ |
| gzip | 0,84 МБ |

Разбивка по разделам (компактный JSON, 5,18 МБ):

| Раздел | Размер | Доля |
|---|---|---|
| `tracks` (снимки игроков) | 4,3 МБ | 85% |
| `grenades` (траектория на каждом тике) | 0,47 МБ | 9% |
| `bomb` | 0,18 МБ | 3% |
| `ticks` | 0,07 МБ | 1% |
| остальное (события, статистика, сводки) | меньше 0,02 МБ | менее 1% |

Внутри `tracks`: координаты `x`, `y`, `z` около 2,3 МБ, углы `yaw`, `pitch` около 1 МБ, `money` 0,54 МБ, `hp` 0,43 МБ, оружие и инвентарь менее 0,04 МБ.

Полный матч дал 19,2 МБ (3,3 МБ в gzip), см. выше: это примерно вдвое меньше оценки спецификации (30-40 МБ).

Если размер станет проблемой, самые дешёвые меры: `money` меняется редко, его можно хранить списком смен; положения кодировать разностями от предыдущего снимка.

## Что проверено тестами

`cargo test --release -p parser-core` (тесты на демках пропускаются без файлов; в debug-сборке полный матч идёт минуты, поэтому запускай в release):

- общие инварианты (`tests/common`) на обеих демках: длины массивов равны `ticks`, шаг снимков 4, hp 0..100, углы и деньги в диапазонах, никто не оживает в раунде, никто не умирает дважды, все индексы игроков и оружия указывают на существующие записи, бомба согласована с причиной раунда (причина 1 значит взрыв, 7 разминирование), у раундов на уничтожение проигравшая сторона не живее одного игрока в конце, итоги статистики равны сумме по раундам;
- полный матч: 24 раунда, у каждого есть победитель и причина, счёт 11:13, пятёрки не расходятся по сторонам, стороны меняются между 12-м и 13-м раундом, числа убийств, гранат и концов бомбы (опорные числа это наш же вывод, внешнего источника нет);
- короткая демка: совпадение числа гранат и областей с событиями демки, побайтное совпадение с эталоном `samples/test_demo.expected.json.gz`, повторяемость вывода;
- плохой ввод (пустой, мусор, чужой формат, обрезанная демка, нет файла) даёт ошибку, а не падение.

## Найдено при проверке на полном матче

- `round_end` в новой демке содержит победителя и причину строками (`"CT"`, `"t_killed"`), в старой числами. Сначала все 24 раунда вышли без победителя; исправлено, поддержаны оба формата.
- Перед первым раундом есть служебный `round_end` с номером 0 без данных, он игнорируется.

## Не проверено

- Овертайм: в обеих демках его нет.
- Матчи без `begin_new_match`, демки с паузами и таймаутами, другие режимы.
- Демки после обновлений игры: формат меняется, зависимость demoparser2 закреплена на коммите.
- Время и память на iPad.
