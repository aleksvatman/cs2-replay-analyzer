# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Состояние репозитория

Спецификация (на русском) остаётся источником истины:

- `parser-doc.md` — спецификация крейта `parser-core`; `docs/format.md` — актуальный формат JSON (что уже реализовано, что в плане).
- `plan.md` — план всего проекта (сервер на Axum, `ios-bridge`, iPad-приложение на SwiftUI). Парсер — лишь первая часть.
- `server-doc.md` — спецификация сервера (API, очередь разбора, хранилище, безопасность, деплой, этапы S1-S9). Реализованы этапы S1 (каркас: конфиг, `/health`, ошибки, остановка), S2 (`storage.rs`: каталог матча, `meta.json`, восстановление после перезапуска) и S3 (`POST /matches`: потоковая загрузка на диск, дедупликация); запуск `cargo run -p server`, тесты `cargo test -p server`.

Реализовано в `parser-core` (этапы 1-9): заголовок, игроки, раунды, снимки каждые 4 тика, экономика, вывод `tickRate`, события (убийства, урон, ослепления) и бомба, включая брошенную, гранаты с траекториями и областями дыма/огня, статистика игроков (`stats.rs`). Замеры: `docs/measurements.md`. Осталось по `parser-doc.md` разд. 7: проверка на полном матче и память/время на iPad (этап 10).

Команды: `cargo test -p parser-core` (интеграционный тест пропускается без `samples/test_demo.dem`, демки в git не лежат); `cargo run --release -p parser-core --example parse -- samples/test_demo.dem [out.json|out.json.gz]` печатает JSON (в stdout, если путь не задан) и прогресс в stderr; примеры `events`, `ticks` и `proj` — отладочные дампы сырых данных demoparser2.

Эталон: `samples/test_demo.expected.json.gz` (полный JSON тестовой демки, сжатый). Тест `output_matches_the_reference_json` сравнивает с ним побайтно. Если формат изменён намеренно, пересоздай эталон командой `parse` выше с выходом `samples/test_demo.expected.json.gz` и закоммить. Без `samples/test_demo.dem` тесты на демке пропускаются. Полный матч (`samples/natus-vincere-vs-falcons-m1-ancient.dem`, 410 МБ, не в git): `cargo test --release -p parser-core --test full_match` (в debug очень медленно).

**Отклонение от спецификации:** по решению владельца в первую версию парсера входят позиция брошенной бомбы, статистика по игрокам и экономика (деньги, закупка, инвентарь). Документы (`parser-doc.md`, `plan.md`, `docs/format.md`) уже обновлены под это решение.

## Процесс

Перед каждым push ветки для PR обновляй `summary.md` (корень репозитория): в нём должно быть актуальное описание сделанного (состояние, что реализовано, тесты, замеры, список PR, что осталось). Коммить его в той же ветке до push, в том числе в PR только с документацией.

Работа над сервером (`server/`) не должна менять `parser-core/`, `samples/`, `docs/format.md` и `docs/measurements.md`. Если изменение парсера действительно нужно, сначала опиши владельцу, что и зачем менять, и дождись подтверждения; без него парсер не трогай. Перед коммитом проверяй: `git diff --stat main -- parser-core samples docs/format.md docs/measurements.md` пуст.

## Архитектура (planned)

`parser-core` — Rust-библиотека: `.dem` → компактный JSON для 2D-повтора. Один и тот же код должен собираться под сервер и под iOS (статическая библиотека через `ios-bridge`), поэтому:

- никаких зависимостей от Axum, Tokio, сети и платформенного кода; только `parser` (ядро demoparser2), `serde`, `serde_json`;
- API синхронный (тяжёлый по CPU); поток выбирает вызывающая сторона. Публично: `parse_file(path, progress)`, `parse_bytes(&[u8], progress)`, `to_json`, `write_json`, `parse_file_to_json`; `progress: Option<&mut dyn FnMut(Progress)>` вызывается на границах шагов (внутри прохода ядро хука не даёт). Мусорный ввод даёт `Err`: проверяется сигнатура `PBDEMS2\0`, паники ядра ловятся `catch_unwind`, поэтому встраивающий код (`ios-bridge`) не должен собираться с `panic = "abort"`;
- ядро demoparser2 принимает `&[u8]`, поэтому потокового чтения нет: файл читается через mmap. Хватит ли памяти на iPad 7 (3 ГБ) — проверить на этапе 9. Ядро не собирает события и состояние сущностей за один проход, поэтому `parse` читает демку трижды (события и ростер, тики игроков, снаряды).
- имена свойств для тикового прохода переводятся через `parser::maps::FRIENDLY_NAMES_MAPPING`; steamid читать как `u64` (в `f64` теряется точность).

Модули: `lib.rs` (интерфейс), `parse_demo.rs` (всё общение с demoparser2: события и тики), `extract.rs` (сырые данные → раунды, снимки, гранаты, бомба), `models.rs` (структуры serde = JSON-контракт), `error.rs`. Тесты — на маленькой демке с эталонным JSON из `samples/`; формат фиксируется в `docs/format.md`.

## Контракт JSON (важные инварианты)

- Обязательное `schemaVersion`; верхний уровень: `map`, `tickRate`, `players`, `weapons`, `rounds`.
- Снимки каждые 4 тика; в раунде один общий массив `ticks`, у каждого игрока массивы `x,y,z,yaw,pitch,hp` той же длины (индекс совпадает с `ticks`).
- Целые числа: координаты и углы в десятых долях; hp 0-100, `hp == 0` значит мёртв (отдельного флага нет).
- Команда хранится один раз на игрока; оружие — список смен `(индекс снимка, id)` + словарь `weapons`.
- События (убийства, урон, ослепления, раунды) — отдельные короткие списки с тиком в каждой записи.
- Гранаты: траектория на каждом тике (излом после удара о стену виден сам), отдельных точек отскока нет; молотов и зажигательная это один тип `fire`.

## Известные особенности данных (не потерять)

- Последний снимок раунда не позже `endTick`, а последнее убийство приходит на тик `round_end`: в `hp` его может не быть, рисовать по `events.kills`.
- Оружие в событиях (`ak47`) и в инвентаре/активном оружии (`AK-47`) называется по-разному, в `weapons` это разные записи; для статистики (этап 7a) нужна таблица соответствия.
- `damage[].healthDmg` сырой: `stats.rs` режет его по предыдущему hp жертвы (hp начинается со 100 в каждом раунде). Урон по своим и самоубийства в статистику не идут.
- События после `endTick` последнего раунда отбрасываются (завершение демки).
- В CS2 нет события отскока гранаты, и отскоки не выводятся: траектория гранаты пишется на каждом тике (`grenades[].ticks/x/y/z`), излом после удара виден сам. Молотов и зажигательная это один тип `fire`. Колонки снарядов ядро отдаёт в `df`, а не в `projectiles` (оно пустое).
- `round_end` бывает в двух видах: числа (старая демка) и строки `"CT"`/`"t_killed"` (новая); `parse_demo.rs` приводит оба к числовым кодам. Перед первым раундом приходит служебный `round_end` с номером 0, он игнорируется.
