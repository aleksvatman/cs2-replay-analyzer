# Приложение для iPad: спецификация и этапы

Документ описывает iPad-приложение (Swift, SwiftUI) и мост `ios-bridge` для локального разбора. Источники: `plan.md` (общий план, разд. 1, 5-7), `docs/format.md` (контракт JSON), `parser-doc.md` (парсер), `server-doc.md` (API сервера), `docs/measurements.md` (замеры). Здесь только то, что нужно для приложения; детали парсера и сервера остаются в их документах.

## 1. Цель и границы первой версии

Приложение открывает матч CS2 и показывает 2D-повтор: радар карты, точки игроков, гранаты, бомбу, убийства, таймлайн раунда и таблицу статистики. **Решение владельца от 2026-11-13 (см. разд. 8a): онлайн-разбор через сервер не делаем.** JSON получается только из локального разбора на устройстве (`LocalParser`, через `ios-bridge`, когда мост будет готов) — пока он не готов, приложение работает на подложенных вручную JSON (`Resources/SampleMatches/`). Приложение рисует по готовому JSON и сырых тиков не видит.

Входит в первую версию:

- список матчей, сводка матча, список раундов;
- таблица игроков по матчу и по раунду (убийства, смерти, помощь, урон, ADR, KAST, процент хедшотов);
- повтор раунда: позиции и углы обзора, hp, оружие, гранаты (траектории, области дыма и огня), бомба (включая брошенную), убийства, урон, ослепления, экономика раунда;
- локальный разбор демки на iPad (офлайн) через `ios-bridge`.

Не входит: фильтр по одному игроку, тепловые карты, раскидки, сравнение раундов, экспорт клипов, учётные записи (токен один), версия для iPhone и Mac (интерфейс не запрещает их, но не проверяется), распространение через App Store (устанавливаем из Xcode на свой iPad).

## 2. Правило: парсер и сервер не меняем

Работа над приложением не меняет `parser-core/`, `server/`, `samples/`, `docs/format.md` и `docs/measurements.md` без подтверждения владельца. Если приложению нужно что-то от них (новое поле JSON, хук отмены разбора, поправка сервера), сначала описываю, что и зачем менять, и жду «да». Исключение по умолчанию одно: новый крейт `ios-bridge/` и его запись в `Cargo.toml` workspace; корневой `Cargo.toml` это общий файл, добавление члена workspace допускается. Перед коммитом проверяю, что `git diff --stat main -- parser-core server samples docs/format.md docs/measurements.md` пуст. Замеры на iPad запишу в `docs/measurements.md` только после разрешения владельца (как было для сервера).

## 3. Стек и требования

- Swift 5.9 или новее, SwiftUI, `@Observable`, Codable, `URLSession`, async/await, MVVM. Рисование: `Canvas` и `TimelineView`.
- Минимум iPadOS 17 (решение из `plan.md`). Сборка: Xcode 16.2, macOS Sonoma 14.5 или новее.
- Тестовое устройство: iPad 7 (A10 Fusion, 3 ГБ памяти, максимум iPadOS 18). Он слабый, и это хорошо для проверки: если работает на нём, работает везде.
- Сторонние Swift-пакеты в первой версии не нужны.
- Установка на свой iPad из Xcode с бесплатным профилем: подпись живёт 7 дней, потом нужна переустановка. С платной учёткой Apple Developer 1 год. Решение за владельцем, на архитектуру не влияет.

## 4. Структура

```
ios-app/                       проект Xcode
  App/CS2AnalyzerApp.swift
  Models/                      Codable один в один как docs/format.md
  Domain/                      MatchSource (протокол), RadarProjection, ReplayClock
  Sources/LocalParser.swift    ios-bridge (этап I9, отложен, разд. 8a)
  Storage/MatchStore.swift     локальный кэш разобранных матчей (этап I6, отложен)
  ViewModels/                  MatchList, MatchDetail, Replay, Settings
  Views/MatchList, MatchDetail, Replay, Settings, Components
  Resources/Maps/              радары и калибровка
  Tests/
ios-bridge/                    Rust-крейт, C-интерфейс (этап I8, отложен)
```

Без онлайн-разбора (разд. 8a) `Networking/` и серверный `TokenStore.swift` из первоначального плана не нужны — источник один, `MatchSource` остаётся протоколом ради чистоты слоёв (сейчас одна реализация — подложенные JSON, затем `LocalParser`), а не ради выбора между сервером и устройством.

Навигация: `NavigationSplitView`. Слева матчи и раунды, справа сводка или повтор. Источник данных скрыт за протоколом `MatchSource` с методами «разобрать файл» (возвращает локальный URL JSON и прогресс) и «получить список/данные». Остальной код про источник ничего не знает.

## 5. Модели и декодирование

Структуры Codable повторяют `docs/format.md`: верхний уровень (`schemaVersion`, `map`, `tickRate`, `players`, `weapons`, `rounds`, `stats`), раунд (`ticks`, `teams`, `tracks`, `events`, `bomb`, `grenades`, `summary`). Кортежи событий (`kills`, `damage`, `blinds`, `carrier`, `drops`, `pickups`, `inventory`, `weapon`) приходят массивами: декодируются через `unkeyedContainer` в именованные структуры. Массивы `x, y, z, yaw, pitch, hp, money` остаются `[Int32]`/`[Int16]` без обёрток, чтобы рисовать по индексу снимка без перебора объектов.

Правила:

- `schemaVersion` проверяется первым. Если версия выше поддерживаемой, показываем понятную ошибку «обновите приложение», а не падаем на разборе.
- Неизвестные поля игнорируются (так формат можно расширять без поломок).
- Единицы: координаты и углы в десятых долях, пересчёт в точки/градусы в одном месте (`RadarProjection`, `ReplayClock`), а не по всему коду.
- Тесты декодирования берут эталон `samples/test_demo.expected.json.gz` (ссылкой из проекта, копировать не нужно) и сверяют число раундов, игроков, суммы по `stats` и несколько событий вручную.
- Скорость декодирования 19 МБ JSON (полный матч) на iPad 7 неизвестна: `JSONDecoder` создаёт много временных объектов. Замерить на этапе I1; если дольше нескольких секунд или памяти заметно больше 2x от размера, декодировать раунды по одному (ленивое чтение с индексом раундов) или написать разбор вручную.
- Память: JSON держим на диске, в памяти только раунд, который открыт, и сводка. Остальные раунды декодируются при выборе.

## 6. Радар и перевод координат

Игровые координаты переводятся в пиксели радара по калибровке карты: `px = (x - pos_x) / scale`, `py = (pos_y - y) / scale` (значения `pos_x`, `pos_y`, `scale` лежат в `overviews/<карта>.txt` игры; в JSON координаты в десятых долях, поэтому делить на 10). Для каждой карты хранится файл калибровки (`<карта>.json`: изображение, `posX`, `posY`, `scale`) и PNG радара.

- Карты для проверки: `de_mirage` (короткая демка) и `de_ancient` (полный матч). Остальные добавляются тем же способом.
- Карты с несколькими уровнями (например, Nuke и Vertigo) имеют второй радар и порог высоты `z`. В первой версии они не делаются; приложение показывает предупреждение, если калибровки карты нет. Структуру калибровки делаем сразу с полем `levels`, чтобы не ломать формат позже.
- Вопрос к владельцу до этапа I3: откуда брать картинки радаров. Они из файлов игры (авторские права Valve); для личного использования их можно взять из установленной игры, но класть в публичный репозиторий не стоит. Предлагаю: положить в репозиторий только калибровку, а картинки добавлять в `Resources/Maps/` вручную (в `.gitignore`), с инструкцией, откуда копировать. Тесты не должны зависеть от наличия картинок.

## 7. Повтор раунда

- Часы повтора (`ReplayClock`): текущее положение это игровой тик, а не индекс. Воспроизведение идёт по реальному времени (`TimelineView`/`CADisplayLink`), скорость 0,25x, 0,5x, 1x, 2x, 4x. Индекс снимка = `(tick - ticks[0]) / 4`, кадр берётся по ближайшему не позже тика.
- Таймлайн: ползунок по тикам раунда, отметки убийств, установки/разминирования бомбы, конца заморозки. Перемотка по клику на событие.
- Рисуются: игроки (цвет по `teams[p]` в этом раунде, стороны меняются на полувремени), направление обзора (yaw), мёртвые серым или скрыты, имя и hp рядом; гранаты по `ticks/x/y/z` (точка полёта и след), области дыма и огня по `area` с началом и концом; бомба по `trackX/Y/Z` до установки и по `bomb.x/y` после; убийства линией убийца-жертва и в ленте; ослепления.
- Особенности данных, которые приложение обязано учитывать: последнее убийство раунда приходит на тик `round_end` и в `hp` не видно, поэтому смерти рисуются по `events.kills`, а не только по `hp == 0`; бомбу можно поставить после `endTick`; игрока без данных тика считать мёртвым; yaw в десятых градуса.
- Названия оружия в событиях (`ak47`) и в инвентаре (`AK-47`) разные записи словаря `weapons`: прямое сравнение id не работает. Нужна таблица соответствия внутри приложения (`WeaponNames`), она же отдаёт иконку.
- Плавность: 16 кадров данных в секунду. Если дёргается, добавляем линейную интерполяцию позиции и углов между соседними снимками (угол переходит через 360 по кратчайшему пути). Сначала проверить глазами на устройстве, не делать заранее.
- Производительность `Canvas`: 10 игроков и до нескольких десятков гранат в кадре; цель 60 fps на iPad 7. Тяжёлое (радар, статичные подписи) рисуется один раз как изображение.

## 8. Сеть (RemoteParser) — не делаем, см. разд. 8a

Ниже — исходный план этапа I5, оставлен для истории и на случай, если решение изменится. Не реализуется, пока владелец не попросит снова.

Использует API из `server-doc.md`, разд. 5. Тело загрузки сырое (`application/octet-stream`), заголовок `Authorization: Bearer <токен>`, `X-File-Name` с именем файла.

- Загрузка: `URLSession.uploadTask(with:fromFile:)` из файла, а не из памяти (демка до 400+ МБ). Фоновая сессия (`URLSessionConfiguration.background`), чтобы загрузка переживала сворачивание приложения.
- Статус: опрос `GET /matches/{id}` раз в 1-2 с (`stage`, `percent`, `error`). Статусы `queued`, `parsing`, `done`, `failed`. Опрос останавливается при уходе с экрана.
- Данные: `GET /matches/{id}/data`, `URLSession` сам разжимает `Content-Encoding: gzip`. Скачивание сразу в файл (`downloadTask`), не в память. `ETag` и `If-None-Match` для кэша (`304`).
- Ошибки сервера (JSON `{"error":{"code","message"}}`) показываются понятным текстом: 401 «неверный токен», 413 «файл больше лимита сервера», 415, 422 «не демка CS2 или не удалось разобрать», 429 и 503 с учётом `Retry-After`, 507, 409 «ещё не готово». Сеть недоступна и таймаут отличаются от ошибок сервера.
- Дубликат: `200` с id существующего матча означает «уже загружено», приложение просто открывает его.
- Токен и адрес сервера: адрес в настройках, токен в Keychain, не в `UserDefaults` и не в логах. Адрес только `https://` (кроме localhost для разработки: исключение ATS только для debug-сборки).
- Удаление: `DELETE /matches/{id}` с подтверждением; локальный кэш удаляется вместе с ним.

## 8a. Решение владельца: без онлайн-разбора (2026-11-13)

Этап I5 (сеть, `RemoteParser`) был реализован (`APIClient`, `ServerModels`, `ServerError`, `TokenStore`, `ServerSettings`, экран настроек адреса/токена, 15 юнит-тестов, проверено вручную против локального сервера — PR №25) и затем отклонён владельцем целиком, до мерджа. Решение:

- Онлайн-разбор через сервер в приложении не делаем. Единственный источник JSON — локальный разбор на устройстве через `ios-bridge` (`LocalParser`).
- `server/` (крейт и вся его логика) из репозитория не удаляется — может понадобиться позже, если решение изменится. Просто больше не используется из приложения, и сетевой код в приложении (`Networking/`, `Storage/TokenStore.swift`, `Storage/ServerSettings.swift`, `Views/SettingsView.swift`) не пишется заново, пока не попросит владелец.
- `ios-bridge` (этап I8 ниже) — большая отдельная работа (Rust `staticlib`, C-интерфейс, сборка под iOS, риск с `demoparser2`); пока над ней отдельно не начинали. До тех пор, пока её нет, разработка приложения продолжается на подложенных вручную JSON (`Resources/SampleMatches/`, как в I2-I4), а не на I8/I9/I6 (хранилище было рассчитано на серверный кэш с `ETag` — для локального разбора его имеет смысл переосмыслить, когда дойдёт очередь).
- Следующий активный этап — I7 (полировка): он не требует ни сети, ни моста, чистая работа над интерфейсом и качеством самого приложения.
- Разделы 8, 9, 10, 11 ниже описывают первоначальный план (сеть, хранилище с кэшем сервера, мост, настройки источника) — читать с поправкой на это решение: актуальны идеи локального разбора и локального хранилища, неактуальны всё, что про сервер/источник/офлайн-откат.

## 9. Локальное хранилище (MatchStore)

Без онлайн-разбора (разд. 8a) `id` всегда локальный (SHA-256 демки — один файл не разбирается дважды), `etag`/перезагрузка с сервера не нужны.

- Каталог в `Application Support`: `matches/<id>/{match.json, meta.json}`; `id` — SHA-256 демки.
- Хранить JSON сжатым или нет: сжатие экономит место (19,2 МБ против 3,3 МБ), но требует распаковки при открытии (`Compression`, `zlib` после снятия gzip-заголовка). Решение принять по замеру времени декодирования (I1 это уже показал быстрым на обоих устройствах, см. `summary.md`); если открытие остаётся быстрым, хранить сжатым.
- Исключить каталог из резервных копий iCloud (`isExcludedFromBackup`) для файлов, которые можно получить заново.
- Контроль размера: настройка «хранить не больше N матчей/МБ», удаление старых по последнему открытию, ручное удаление.
- Если `schemaVersion` в кэше ниже текущей (новая версия `ios-bridge`/парсера), запись помечается устаревшей: локальный разбор исходной демки заново (если она ещё доступна по security-scoped URL) или явное предупреждение пользователю.
- Исходные `.dem` приложение не копирует и не хранит. При локальном разборе открывается файл по security-scoped URL из «Файлов».

## 10. Локальный разбор: `ios-bridge` и `LocalParser`

**Этап I8 (мост) сделан.** `ios-bridge/` — новый Rust-крейт (`crate-type = ["staticlib", "rlib"]`), единственная зависимость `parser-core` (как библиотека, без изменений) плюс `flate2` для `.json.gz`. Без Tokio, Axum и сети.

C-интерфейс (реализован, `ios-bridge/src/lib.rs`):

- `int32_t cs2_parse_file(const char *path, const char *out_path, Cs2ProgressCallback progress_cb, void *user_data)` разбирает демку и пишет gzip-сжатый JSON в `out_path` (перезаписывает, если файл уже есть); 0 — успех, иначе код ошибки (`Cs2Status`: 1 — неверный аргумент/путь, 2 — ошибка ввода-вывода, 3 — ошибка разбора, 4 — паника пересекла границу C, это резерв на случай сбоя внутренней защиты).
- `char *cs2_last_error(void)` — текст последней ошибки этого потока (строка Rust, забирается один раз: повторный вызов без новой ошибки вернёт `NULL`), `void cs2_string_free(char *s)` освобождает её.
- Прогресс: `typedef void (*Cs2ProgressCallback)(uint32_t stage, uint32_t percent, void *user_data)`, стадии как в `parser_core::Stage` (0 Events, 1 Players, 2 Grenades, 3 Assemble, 4 Done); в Swift (этап I9) оборачивается в `AsyncStream`.
- Результат пишется в файл, а не возвращается строкой, чтобы JSON не жил в памяти одновременно в Rust и Swift. Вызывающая сторона (I9) должна звать из `Task.detached` с приоритетом `.userInitiated`, не с главного потока — сама функция синхронная и ничего не знает про потоки.
- Паники не пересекают границу C: `parser-core` уже ловит их `catch_unwind`, `cs2_parse_file` оборачивает весь вызов ещё одним `catch_unwind` (на случай паники в самом мосте — например, неверный путь). Сборка с `panic = "abort"` запрещена нигде в зависимостях этого крейта (иначе `catch_unwind` не работает); в этом workspace профиль по умолчанию (unwind), менять не пришлось.
- Отмены в парсере нет (ядро не даёт хука внутри прохода). Кнопка «Отмена» в приложении (этап I9) отпускает интерфейс и отбрасывает результат, но вычисление дойдёт до конца и удержит память; это нужно честно показать пользователю. Хук отмены потребовал бы изменения `parser-core`, поэтому только с подтверждения владельца и только если замеры покажут необходимость.

Тесты (`ios-bridge/tests/ffi.rs`, `cargo test -p ios-bridge`): полный разбор `samples/test_demo.dem` через `cs2_parse_file` с проверкой, что колбэк прогресса вызывается и результат побайтово совпадает с `parser_core::write_json` (пропускается без демки, как у `parser-core`); несуществующий путь и `NULL`-путь возвращают ожидаемый код ошибки и непустой `cs2_last_error`, без паники. Собирается и проходит на хосте (FFI не зависит от архитектуры) — кросс-компиляция под iOS проверяется отдельно, сборкой, а не тестом (ядро `demoparser2` всё равно не умеет запускаться вне demoparser2-разбора на хосте без реальной демки на устройстве).

Сборка (`ios-bridge/build-xcframework.sh`, проверено):

- Цели: `aarch64-apple-ios` (устройство) и `aarch64-apple-ios-sim` (симулятор на Apple Silicon) — `x86_64-apple-ios` не понадобился (Intel-симулятор не используется). `cargo build --release` под оба таргета, заголовок генерирует `cbindgen` (`ios-bridge/cbindgen.toml`), затем `xcodebuild -create-xcframework` пакует обе `.a` с общим заголовком в `ios-bridge/build/IosBridge.xcframework` (каталог не в git, собирается скриптом).
- Риск №1 (сборка `demoparser2` под iOS) **не подтвердился**: `cargo build -p parser-core`/`-p ios-bridge` под оба таргета (debug и release) проходит без единой правки — ни в `parser-core`, ни в зависимостях. Протестировано на закреплённом в `Cargo.toml` коммите demoparser2 (том же, что проверен сервером и примерами парсера).
- Риск №2 (размер `.a`) не стал проблемой на этапе сборки библиотеки; включение `.xcframework` в размер самого приложения (`CS2Analyzer.app`) не проверялось — это часть I9, когда мост туда реально попадёт.
- Проверка «вызов из маленькой программы на симуляторе» (`ios-bridge/smoketest/`): C-программа (`main.c`) собирается `clang` под `iphonesimulator`, линкуется против симуляторного среза `.xcframework` и запускается через `xcrun simctl spawn` — то есть реально выполняется в рантайме симулятора, а не только компилируется под него (это отдельная проверка от `cargo test`, которая гоняет FFI на хосте). Вызов `cs2_parse_file` на `samples/test_demo.dem` под симулятором дал JSON, побайтово совпадающий с `samples/test_demo.expected.json.gz`. Скрипт: `ios-bridge/smoketest/run-on-simulator.sh [<симулятор>]`.
- Память и время на устройстве (footprint, 40-55 с оценка) — не измерялись, это этап I10 (замеры на iPad 7), который зависит от I9 (там будет реальный путь выбора `.dem` пользователем).
- Выбор файла (`fileImporter`, `startAccessingSecurityScopedResource`, iCloud Drive) — часть I9, ещё не реализована.

## 11. Настройки

Без онлайн-разбора (разд. 8a) выбора источника нет — разбор только на устройстве, раздел упрощается:

- Максимальный размер кэша, очистка кэша.
- Матчи в кэше открываются без сети (приложение и так всегда офлайн).
- Диагностика: версия приложения, `schemaVersion`, версия `ios-bridge`, кнопка «скопировать журнал ошибок» без путей к файлам пользователя.

## 12. Тестирование

- Юнит-тесты (XCTest, без устройства): декодирование эталона, `RadarProjection` (известные точки карты в известные пиксели), `ReplayClock` (индекс снимка по тику, границы раунда, смена скорости), `WeaponNames`, `MatchStore` (кэш, устаревшая схема).
- Снимки интерфейса (по желанию): рендер `Canvas` одного кадра в изображение и сравнение; в первую версию не обязательны.
- Устройство: на iPad 7 замерить время и память (Instruments: Allocations, Memory Graph, `os_proc_available_memory()`), проверить поворот экрана, фон/блокировку, нехватку памяти (jetsam).
- Тестовые данные не должны требовать `.dem` в git: полный матч и короткая демка берутся из `samples/` на машине разработчика.

## 13. Риски

- Сборка `demoparser2` под iOS (разд. 10): может не собраться или потребовать правок; проверяется первой.
- Память и время разбора на iPad 7 (разд. 10): возможно, локальный разбор полного матча там нереален; без сервера (разд. 8a) это означает, что такие матчи пока нельзя будет открыть вообще — owner предупреждён.
- Скорость и память `JSONDecoder` на 19 МБ (разд. 5).
- Плавность 16 кадров в секунду и угловатость траекторий гранат (разд. 7).
- Радары: нужны картинки и калибровка каждой карты, многоуровневые карты не входят в первую версию.
- Формат демок и JSON меняется: `schemaVersion` проверяется.
- Авторские права на радары и иконки оружия: не публиковать в репозитории без решения владельца.
- Подпись и установка: срок жизни бесплатного профиля (разд. 3).

## 14. Этапы разработки

Каждый этап это отдельная ветка и PR; перед push обновляется `summary.md`; push и PR только после «да» владельца. Приложение сначала делается на готовом JSON, без сервера и моста. Сквозная нумерация плана проекта (I1-I10) ниже — исходная, из `plan.md`, разд. 7; статус каждого этапа после решения из разд. 8a указан отдельно.

- I0. Подготовка. Проект Xcode в `ios-app/` (iPadOS 17, iPad), `.gitignore` для `xcuserdata`/`DerivedData`, пустой `NavigationSplitView`, запуск на симуляторе и на iPad 7. Проверка: приложение стартует на устройстве. **Сделано.**
- I1. Модели и декодирование. Codable по `docs/format.md`, проверка `schemaVersion`, тесты на эталоне, замер времени и памяти декодирования полного JSON на симуляторе и устройстве (JSON полного матча получить командой `parse` из `CLAUDE.md`). Решения: сжатый ли кэш, ленивое чтение раундов. **Сделано.**
- I2. Список матчей и статистика. Список из локальных JSON (пока подложенных вручную), сводка матча (карта, счёт, раунды), таблица игроков из `stats`, раунды со сводкой `summary`. **Сделано.**
- I3. Радар и проекция. `RadarProjection`, калибровка `de_mirage` и `de_ancient`, показ статичной карты с точками игроков одного снимка. Решить вопрос про картинки радаров (разд. 6). **Сделано.**
- I4. Повтор раунда. `ReplayClock`, `Canvas`, ползунок, скорость, события убийств, гранаты, бомба, область дыма и огня, ослепления. Таблица `WeaponNames`. Проверка плавности на устройстве; решение про интерполяцию. **Сделано.**
- I5. Сеть (`RemoteParser`). **Отменено решением владельца (разд. 8a, 2026-11-13).** Было реализовано и проверено (PR №25), но отклонено до мерджа — приложение не ходит в сеть.
- I6. Хранилище и кэш. `MatchStore`, устаревшая схема, ограничение размера, удаление (без `ETag` — он был частью сетевого плана, разд. 8a). **Отложено** до момента, когда появится локальный разбор (I8-I9) и будет что кэшировать, кроме подложенных вручную JSON.
- I7. Полировка. Ошибки и пустые состояния, индикаторы, иконки оружия, доступность (Dynamic Type, VoiceOver там, где применимо), поворот экрана, тёмная тема. **Сделано** (PR №27).
- I8. Мост `ios-bridge`. Сначала проверка сборки `parser-core` под `aarch64-apple-ios` и `aarch64-apple-ios-sim`; затем C-интерфейс, заголовок, скрипт XCFramework, тест вызова из маленькой программы на симуляторе. Если сборка невозможна без правок парсера, остановиться и спросить владельца. **Сделано** — см. разд. 10 (риск №1 не подтвердился: `demoparser2` собирается под оба таргета без правок).

Переключателя источника и офлайн-отката больше нет (разд. 8a, 11) — источник один, устройство. Закрывает этап 10 парсера (`parser-doc.md`, разд. 7). **Отложено** — зависит от I9.
